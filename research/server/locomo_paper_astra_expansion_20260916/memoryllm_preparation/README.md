# MemoryLLM full LoCoMo preparation

This package prepares the released MemoryLLM Llama3 chat model for all1,986 original source IDs, plain prompting, greedy48-token generation and the existing Astra scoring route. It is a reconstruction of the missing Encbank-paper MemoryLLM driver; the method remains an out-of-backbone diagnostic. Root owns all GPU submissions and scoring.

The driver uses the official pinned MemoryLLM implementation unchanged. It restores a GPU-resident copy of checkpoint memory and its initialization flag before each conversation, uses seeded official memory updates over full history, then answers every question without updating that memory. The public LongBench example instead resets per example and reserves a final prompt suffix. Our conversation-memory adaptation is explicit, and is not claimed as the historical Encbank invocation. All1,986 plain document-plus-question concatenations match existing inputs exactly. Llama3 tokenization is performed anew; Qwen token IDs are never reused. No answer, category or evidence labels appear in inference inputs.

CPU checks cover all source IDs, lossless chunk boundaries, rejection of label contamination and unsafe short injection, official SDPA forward/generation with both learned adapters, generation preserving memory exactly, and repeatable seeded reset. These are synthetic CPU checks; no real checkpoint was loaded, no GPU initialized and no benchmark answer generated.

The public weight downloader is CPU-only. First attempt verified shards1–2 and then received HTTP429. The saved failure is infrastructure evidence only. The second owner is in `remote_download_resume_receipt.json`; it waits300seconds initially, uses one worker and honors Retry-After with exponential backoff. Its authoritative remote status is `memoryllm_preparation/download_status.json`; per-file retry records are in `memoryllm_preparation/download_status/`. Do not launch generation until it reports COMPLETE and the runtime qualification is complete.

The allocated L20D architecture requires the existing validated torch2.10.0+cu128 binaries. The candidate interpreter is `/srv/encbank/qencbank_runtime_20260911/memoryllm_torch210_20260916/bin/python`; it has isolated transformers4.48.2 and peft0.10.0, with the existing Torch installation reused read-only. The separately prepared upstream torch2.5.1+cu124 environment and its CPU evidence are retained but are not approved for this hardware.

The frozen `plan.json` gives exact model/input/runtime/output paths and limitations. `run_locomo_memoryllm.py` without `--execute-gpu` verifies inputs only. For formal execution, root should use the registered scheduler/admission route, a distinct singleton job name, one visible GPU, at least30GiB free at model load, and the plan's arguments. Existing predictions require explicit `--resume`; a complete1986-item set refuses duplicate loading. Generation records source IDs, unchanged text and token IDs, hardware identity, load timing, natural TTFT/throughput, phase allocator peaks and available device memory. Full-device peaks are left null rather than inferred from allocator data.

No alpha64 adapter has been substituted; this preparation concerns only MemoryLLM.

Preparation only: this is not a frozen or launch-ready formal package. Torch2.10 CPU qualification now passes, but weights are still pending and scheduler/resource admission is not yet bound. One visible GPU and30GiB free alone are insufficient: root must attach the registered no-other-worker,45-second stable-idle,free-memory and native-cap guard before submitting. Do not invoke standalone --execute-gpu as a substitute.
